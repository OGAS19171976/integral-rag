# integral-rag — 一元积分的「检索 + CAS + 验证」求解系统

给一道积分(LaTeX 或纯文本),系统找出该用什么方法、调用符号引擎算出来、
**并且独立验证结果没错**;算不出来就明确拒答,不编式子。

支持三类:

| 类型 | 例子 | 真值来源(验证靠什么) |
|---|---|---|
| **不定积分** | `\int \frac{x^{2}}{\sqrt{1-x^{2}}} dx` | 求导回验 `F'(x) ≡ f(x)` |
| **定积分** | `\int_{0}^{\infty} \frac{\sin x}{x} dx` | 高精度数值求积(一个数对一个数) |
| **含参积分** | `\int_{0}^{\infty} x^{s-1}e^{-x} dx = \Gamma(s)` | 数值求积 + 参数取值扫描 + 积分号下求导的数值检查 |

```bash
$ python demo.py "\int_{0}^{\infty} \frac{\sin x}{x} dx"

① 结构特征
   区间:[0,∞);函数族:三角;形态:商式;信号:oscillatory
② 检索命中(定积分方法卡片 top-4)
   1. [ 9.13] def_standard_dirichlet — Dirichlet 型 ∫_0^∞ sin(ax)/x dx = π/2 (a>0)
③ 方法指导(来自 top-1 卡片)
   适用: 被积函数是 sin(ax)/x 形式,x 从 0 积到 ∞。注意它只是**条件收敛**…
④ 结果与验证
   ∫_{0}^{∞} sin(x)/x dx = pi/2
   ✅ 已验证 · 证据链:数值核对通过(相对误差 0.00e+00,方法 quadosc)
⑤ 数值层(定积分的独立真值来源)
   结论:收敛 ≈ 1.5707963267949(quadosc)
   · |f| 在无穷远处趋于 0,振荡积分可用 quadosc
```

## 1. 为什么不是「直接调 SymPy」,也不是「纯 RAG」

**纯 RAG 做不了积分。** 积分是过程性任务,不是查表任务:检索到一道长得像的题,
不代表方法一样(`∫x·eˣdx` 和 `∫x·ln x dx` 字符重合度很高,但一个把指数塞进微分、
另一个把对数留下)。而积分表覆盖不到的形式是无限的。

**只调 SymPy 也不够。** 实测在教科书级题目上 `sp.integrate` 能吃掉七成左右;
它不解释;而且**它有时候会给出发散的值或者错误的答案**(第 6 节有真实案例),
甚至会在一部分积分上无限期地卡住不返回。

所以这里是三件事分开做:

| 角色 | 由谁承担 | 职责 |
|---|---|---|
| 想出方法 | 检索层(方法卡片) | 决定"该用哪一招" |
| 算出结果 | 符号引擎(SymPy) | 真正做代换、求原函数 |
| 确认没错 | 验证层 | **唯一有权说"这个能用"的角色** |

三条设计纪律贯穿全部代码:

1. **任何进入最终答案的东西都必须先过验证层。** 检索到的方法只是"建议",
   CAS 的结果只是"候选",验证器点头了才算答案。
2. **拒答是合法结果。** 算不出来就说算不出来,判出发散就报发散,
   绝不编一个看起来像样的原函数或者一个看起来很正常的有限值。
3. **每一层都要能说清理由。** 检索为什么推荐这张卡、这一步为什么被否决,
   都能打印出来给人看。

### ② 为什么检索靠"结构"而不是"文本相似度"

用 LaTeX 字符串的相似度来判断"该用哪个积分方法",几乎没有预测力:
`x*sqrt(1-x^2)` 和 `x*log(x)` 字符上毫无关系,方法(三角替换 / 分部积分)完全不同。

真正有预测力的是结构。所以这里把问题映射成一个离散签名:

```
∫ x²·√(1−x²) dx   →   函数族:多项式/根式;形态:乘积;根号:√(a²−x²)型;信号:binomial_power
∫_0^π x·sin x/(1+cos²x) dx
                  →   区间:[0,π];函数族:多项式/三角;形态:乘积;信号:even_odd/oscillatory
```

**定积分还多一个一等公民:区间类型。** 定积分的方法很大程度上由区间决定 ——
对称区间想到奇偶性、`[0, π/2]` 想到 Wallis/Beta、`[0, ∞)` 想到收敛性和
Frullani/Gamma 形状。签名的每个字段都能打印给人看,所以"为什么推荐这张卡"永远可解释。

### ⑥ 定积分的验证:换了一条更强的证据链

不定积分靠求导回验;定积分没有导数可求,但它有一个**更强**的真值来源:
高精度数值求积。定积分的结果就是一个数,数值算出来是另一个数,对得上就是对得上。

**但数值求积本身很容易骗人。** 实测 `mpmath.quad` 单独使用会给出:

| 积分 | 真值 | `mp.quad` 单独使用 |
|---|---|---|
| `∫_1^∞ dx/x` | 发散 | **125**(会假阳性!) |
| `∫_0^∞ sin x/x dx` | π/2 ≈ 1.5708 | **8.88** |
| `∫_0^∞ cos(x²)dx` | 0.62666 | **3.9e53** |
| `∫_{-1}^{2}\|x\|dx` | 2.5 | 2.49999(折点没切开) |

所以 `quadrature.py` 不是"调一下 quad",而是把一整套策略组合起来:

```
① 在折点(Abs/floor 的拐点)与极点处把区间切开
② 端点奇点交给 tanh-sinh,端点是一阶极点时用 ε 逼近序列判发散
   (tanh-sinh 遇到 ∫_0^1dx/x 不会报错,而是给出 102 这种"看起来很正常的收敛值")
③ 端点有瑕点时先换元抹平:x = u²  (∫_0^∞ dx/(√x(1+x)) 由 x^{-1/2} 变成光滑的 2/(1+u²))
④ 无穷限用**截断序列看趋势**:增长 → 发散;差值收缩 → 收敛
⑤ 恒定频率的振荡用 quadosc,并且是"头部 quad + 尾巴 quadosc"再交叉验证
   (整体交给 quadosc 只有 3e-3 精度,切尾之后能到 1e-20)
⑥ x^p 型加速振荡先换元成线性频率再交给 quadosc
⑦ 衰减判据:频率恒定的振荡若 |f| 不趋于 0,直接判发散
```

**三种结论,不含糊:** `convergent(值)` / `divergent(判据)` / `inconclusive`。
第三种是关键 —— 数值上判不了的时候,调用方必须**放弃**验证,
而不是把它当成"验证失败"或者"通过"。这样验证器既不会假阳性,也不会假阴性。

### ⑦ 含参积分能做什么

"含参积分"在数学分析里主要是一套理论(连续性、可微性、一致收敛)。
这套系统能做、并且**能验证**的是三件:

1. **算出含参积分的闭式,并把成立条件作为答案的一部分报出来。**
   `∫_0^∞ x^{s−1}e^{−x}dx = Γ(s)` 只在 `s>0` 成立 —— 条件不是废话。
   做法:提取 SymPy `Piecewise` 里的条件,再加上主动用"敌意参数值"探测
   (在 `s=−1.5` 处数值上发散 → 报"`s` 必须使积分收敛")。

2. **数值验证"积分号下求导"是否成立。** 左边用中心差分数值求导、
   右边对 `∂f/∂t` 直接数值求积,在若干个 `t` 上对比。
   实测 `∫_0^∞ sin(tx)/x dx = π/2`(t>0)会被正确**否证**:
   右边 `∫_0^∞ cos(tx)dx` 数值上不存在,说明交换次序不合法 ——
   这正是教科书里的经典陷阱。
   **必须说清楚:这不能证明一致收敛。** 它只能在有限个点给出"看起来合法"的
   证据,以及在某个点直接否证。数学证明仍要靠 Weierstrass 判别法那一套;
   数值验证的作用是防止把一个不成立的交换次序当成合法操作。

3. **用费曼技巧(对参数求导)真的把积分算出来。**
   `∫_0^∞ (arctan(ax) − arctan(bx))/x dx` 这类,SymPy 直接放弃,
   对参数求导之后积分立刻变简单;常数项由"某个参数值上被积函数恒为 0"
   这条精确理由定出(而不是数值凑),最后仍然要过数值验证。

### 超时:不可控的符号计算必须能被放开

SymPy 的 `integrate` 没有超时机制,个别积分会让它陷进去出不来 ——
实测 `∫_0^1 ln(1+x)/(1+x²)dx` 十几分钟不返回。

`timeout.py` 用**守护线程**给每一处可疑的符号计算套上超时。
不用子进程,是因为 Windows 上 multiprocessing 用 spawn 启动会重新导入 `__main__`,
调用方脚本没有 `if __name__ == "__main__"` 保护就会无限递归创建进程 ——
不该把这种负担甩给使用者。代价是超时后那个线程还在后台跑(Python 无法中断
C 层循环),它是 daemon 不会阻止进程退出。

> **这个代价不是"可以接受"那么轻。** 第三轮实测发现:跑飞的线程会继续
> 抢 CPU 和 GIL,把**后面每一道题**都拖慢 —— 同一道题单独跑 26.3 秒,
> 放在 50 题的串行评估里要 62.1 秒(慢 2.4 倍)。第 6c 节记录了对策,
> 以及为什么本该最彻底的"进程隔离"在当前沙箱里走不通
> (Windows 的 `multiprocessing` 用命名管道,而沙箱拒绝创建它)。

作为库调用:

```python
from integral_rag import analyze

# 不定积分
r = analyze(r"\int \frac{x^{2}}{\sqrt{1-x^{2}}} dx")
print(r.ok, r.result)          # True  -x*sqrt(1 - x**2)/2 + asin(x)/2

# 分步解答(§6h):换元 → 求原函数(含 t)→ **回代** → 验证,是结构化字段
r2 = analyze(r"\int \frac{1}{2+\cos x} dx")
print(r2.ok, r2.result)        # True  2*sqrt(3)*atan(sqrt(3)*tan(x/2)/3)/3
for step in r2.as_dict()["steps"]:
    print("·", step)
# · 原积分 ∫1/(cos(x) + 2) dx
# · 换元:万能代换 t = tan(x/2) · 依据卡片 weierstrass_substitution ⟹ 化为 ∫2/(t**2 + 3) dt
# · 求原函数:对代换后的积分求原函数,得到 2*sqrt(3)*atan(sqrt(3)*t/3)/3(含变量 t)
# · 回代:把 t 换回 x —— …(不定积分**必须**做这一步,否则答案还留在代换变量里)
# · 验证:……符号验证:求导后的差式经 simplify 化简为 0
print(r2.render())             # 终端里 ⑥ 就是这条链,规则库路径挂在"求原函数"下面

# 定积分(analyze 自动分派,返回 DefiniteReport)
r = analyze(r"\int_{0}^{\infty} x^{s-1} e^{-x} dx")
print(r.ok, r.result)          # True  gamma(s)
print(r.solution.conditions)   # ['Γ(s) 要求 s > 0', 's 必须使积分收敛(s=-1.5 时发散)']
print(r.solution.numeric.describe())   # 收敛 ≈ 1.77...(smooth-endpoint → truncation-sequence)

# 分步解答(§6g):换元链、求解、验证都是结构化字段,不只是给人看的一行字
r = analyze(r"\int_{0}^{1} \frac{\ln(1+x)}{1+x^{2}} dx")
for step in r.as_dict()["steps"]:
    print("·", step)
# · 原积分 ∫_{0}^{1} log(x + 1)/(x**2 + 1) dx
# · 换元:三角替换 x = tan t(分母含 1+x²) · 令 x = tan(t) · 依据卡片 … ⟹ 化为 ∫_{0}^{pi/4} …
# · 求解:在内层问题上用「区间再现公式」得到 pi*log(2)/8
# · 等值性:换元只是把这个积分改写成另一个**等值**的积分…无需回代
# · 验证:对**原积分**做高精度数值求积核对 —— 数值核对通过(相对误差 0.00e+00)
print(r.render())              # 终端里渲染成 ①…⑦ 的完整报告,④ 就是解题步骤

# 积分号下求导的数值验证
from integral_rag.parametric import verify_derivative_under_integral
import sympy as sp
x, t = sp.Symbol("x", real=True), sp.Symbol("t", positive=True)
for c in verify_derivative_under_integral(sp.sin(t*x)/x, x, t, 0, sp.oo):
    print(c.agree, c.note)     # False  右边 ∫∂f/∂t dx 数值上不存在…交换次序不合法
```

### 4.1 扩充语料(详见 §6d、§6e)

定积分的检索一直是短板(top-1 方法族命中 68%)。这一轮把语料从 24 张 / 72 例题
扩到 **27 张 / 128 例题**,做了三件事:

1. **新增 3 张缺方法的卡片**:Frullani 积分、倒代换 `x → 1/t`、
   对数正弦积分(§6e,这一张要求**先补上求解能力**才能建)。
2. **补 50 条例题**,集中在标准结果与各方法族上。例题不是装饰:检索会给
   "结构完全吻合的例题"额外加分,所以每多一条覆盖真实形状的例题,
   就等于多一个可命中的锚点。
3. **修三处触发器缺陷**(都是实测出来的,不是猜的):
   * `def_newton_leibniz` 原来四个触发字段**全是空数组**。而评分器会跳过
     空字段 —— 于是这张"通用兜底"卡永远拿 0 分,连自己的例题都赢不回来
     (`∫_0^1 x²dx` 被判给了"对称性",可区间 `[0,1]` 根本不对称)。
   * `def_improper_split` 原来只声明 `interval: ["finite"]`,但它自己的三道例题
     区间分别是 `unit` / `symmetric` / `unit` —— **在自己的例题上全部对不上**。
   * `def_convergence_p_test` 原来把 `unit`/`finite` 也写进了区间,
     于是在 `∫_1^e 1/x dx` 这种"有界、收敛、能直接算"的题上也抢 top-1。
     p 判别法是**反常积分**的工具,已收回到无穷限。

**一条硬规矩:写进语料的例题必须能真的解出来。** 所以每条候选例题都先跑过完整
流水线,只收"求解+验证通过"的。

这条规矩当时挡下了一个看似该有的卡片:`∫_0^{π/2} \ln(\sin x)dx`
(Euler 对数正弦积分)三道候选**全部解不出来** —— 那是**能力**缺口,不是语料缺口。
于是它被记进待办,**没有建卡**。

> 后来它被补上了,**但顺序是先补能力、再补卡**(§6e):先加 `_strategy_log_sine`
> 标准结果策略让这一族真的能算,然后才把 6 条例题写进卡片。
> **反过来做(先建卡)只会让语料看起来完整,系统依然不会做这道题。**

另外剔除了两条边缘不稳定的例题:`∫_0^∞ (cos ax − cos bx)/x dx` 单独跑能出结果
(30 秒),放进自测就失败;`∫_0^∞ e^{-tx}\sin x/x\,dx` 在特定求解路径下会卡住
(见 6d.6,那是**真实的健壮性缺口**,不是例题的错)。

**如果没有这条规矩,这一轮本可以多报 2 张卡、多 8 条例题 —— 那些数字会更好看,
但它们是假的。**

### 4.2 语料字段是**为检索设计**的

每张卡片的字段不是给人读的百科条目:

```json
{
  "id": "def_symmetry_even_odd",
  "family": "symmetry",
  "priority": 15,
  "triggers": {
    "interval": ["symmetric"],     ← 定积分特有:区间是一等公民
    "has_radical": [],
    "has_func": [],
    "form": [],
    "misc": ["even_odd"]
  },
  "when":     "可操作的判别信号",
  "recipe":   "分步做法,含具体公式",
  "pitfalls": "真实高频错误",
  "examples": ["\\int_{-1}^{1} x^{3} dx", "\\int_{-a}^{a} x^{2} dx"]
}
```

`schema.py` 用代码固定了所有枚举值,`build_corpus.py` 逐条校验并对**每一条例题跑一遍
完整流水线**。语料写得好不好是一个可以自动跑出来的数字 —— 这是它敢把卡片写作
外包出去(由另一个 agent 撰写)的原因:写错的卡片会立刻暴露在自命中率上。

## 6. 踩过的坑(这一节可能是最有价值的部分)

以下每一条都是**实测暴露出来的**,不是假想的。

### 6.1 SymPy 真的会给出错误答案

`∫√(x²−a²)/x dx` 直接调用 `sp.integrate`,返回一个 `Piecewise`,其主分支在
`x = −3.7` 处的导数是 **+0.835**,而被积函数是 **−0.835** —— 符号反了。
这条错误正是被数值验证抓出来的;如果没有验证层,这就是一个"看起来非常专业"的错误答案。

### 6.2 tanh-sinh 会把发散积分算成一个"很正常的有限值"

`∫_0^1 dx/x` 发散,而 `mp.quad` 会返回 **102.02**。
这是最危险的一类数值陷阱:结果是有限的、量级也不离谱,直接拿去比对就会假阳性。
修法是在每条子区间的端点上先用数值探针查有没有极点,再用 ε 逼近序列判一次
(`∫_ε^1 dx/x = −ln ε` 会无界增长,`∫_ε^1 x^{-1/2}dx = 2(1−√ε)` 不会)。

### 6.3 截断点从 0 开始会让整条序列失效

`∫_0^∞ e^{-x}dx` 的截断序列原来是 `[0*10, 0*100, …] = [0,0,0,…]` ——
因为有限端点是 0,`start*10^k` 永远是 0。序列退化成全零,什么也判不出来。
修法是用**绝对**尺度:`base = max(|start|, 1)`。

### 6.4 "完全稳定的序列"被误判成振荡

`e^{-x²}` 的部分积分在 `R=10` 时就已经到机器精度,后面的差值全是 0。
原来的判据里"差值不收缩"会把这些 0 当成振荡。
修法是先加一条:`最大差值 ≤ 1e-12 × 量级 → 直接判收敛`。

### 6.5 对数发散长得太温和,得单独认

`∫_1^R dx/x = ln R` 的序列 `[2.30, 4.61, 6.91, 9.21, …]`
单项看着都很温和,末项除以中位数也才 1.5 倍,"爆炸式增长"的判据完全抓不住。
它的特征是**单调递增而且增量不收缩** —— 得专门加这条。

### 6.6 参数没被代进去,而数值层"兴高采烈地"报了个 0

`evaluate(f, x, 0, ∞)` 里参数用**字符串键**(`{"t": 0.5}`),
而代码拿它去和 `f.free_symbols` 里的 Symbol **对象**比对 ——
`"t" in {Symbol('t')}` 永远是 False,参数就悄悄没代进去。
于是 lambdify 出来的是个需要两个参数的函数,每次求值都抛异常;
而 `_guarded`(本意是"把端点上的 nan 当成 0")把每次异常都当成 0,
积分看起来恒等于 0,数值层报告 **"收敛 ≈ 0"**。
两个 bug 叠在一起就成了一个静默的假阳性。

修法两处:(a) 按**符号名**匹配参数;(b) `_guarded` 必须设失败次数上限,
超过就重新抛出,让上层如实报"无法判定"。**"把失败伪装成 0"是非常危险的设计。**

### 6.7 `|...|` 会被 Python 当成按位或

LaTeX 里绝对值就写成 `|\sin x|`。不处理的话 `|` 直接语法错误。
修法是用栈配对把 `|...|` 转成 `Abs(...)`。

### 6.8 `\b` 在 `\int_` 处不成立

`\int` 后面紧跟 `_`(积分上限)时,`\b` 词边界**不匹配** —— 因为下划线是单词字符。
于是正则 `\\int\b` 抓不到 `\int_{0}^{1}`,`\int` 完好无损地留下来,
后面的 `{`→`(` 替换把上限变成 `_(0)**(1)`,解析就炸了。改用 `(?![A-Za-z])`。

### 6.9 迭代 `Union(ImageSet(...))` 会死循环

`sp.singularities` 对周期函数返回的不是点,而是**无穷族**:
`sin x/(sin x+cos x)` 的奇点集是 `Union(ImageSet(Lambda(_n, 3π/4 + 2nπ), …), …)`。
对这个集合做 `for point in ...` 会触发无限集合的枚举,直接卡死 ——
而且守卫代码根本没机会执行,因为卡的是迭代本身。
修法:只能走 `.args` 递归,并且只接受"明确的数值点"。

### 6.10 `sp.simplify` 在超越式上会卡死

只是在问"分母是不是恰好等于 `x`",却对 `sin x + cos x − x` 调了 `sp.simplify` ——
它会尝试大量恒等变换,几分钟不返回。
修法:相等判断先做廉价的结构检查,差值里含超越函数就直接判否。

### 6.11 `sp.integrate` 会在某些积分上无限期卡住

`∫_0^1 ln(1+x)/(1+x²)dx` 实测十几分钟不返回。
**Python 线程杀不掉 C 层的循环**,所以只能靠"守护线程 + 放弃等待"来控制,
并且要给每一层都设超时和总预算。`solve.py` 里每一次 `_try_integrate`
和 `definite.py` 里每一条策略都套了闸。

### 6.12 Piecewise 里含 `Integral`,不代表答案不可用

SymPy 常返回 `Piecewise((π/sin(πs), s<1), (Integral(...), True))` ——
整个表达式确实"含 Integral",但**第一个分支是完全可用的**。
先判断 `raw.has(Integral)` 就把这种答案白白丢掉了。
修法:先从 Piecewise 里拆分支,拆不出来再看有没有 Integral。

### 6.13 符号没有假设属性,会静静地毁掉整条含参链路

参数识别用的是 `sym.is_real`。SymPy 的 `auto_symbol` 给未声明的名字创建的是
**没有任何假设**的符号,`is_real` 于是是 `None`(不是 `True`)——
参数被当成不存在,`∫_0^∞ x^{s-1}e^{-x}dx` 的答案 `Γ(s)` 明明摆在那里却验不了。

修法:照常解析,解析完给无假设的自由符号补上 `real=True`。
**注意不要试图替换 `auto_symbol` 本身** —— 它产生的是 Symbol *对象* token,
后续 `implicit_multiplication` 等变换依赖那套约定,自己写一个会在
`untokenize` 处炸成 `unsupported operand type(s) for +=: 'Symbol' and 'str'`。
(这个坑我踩了两次。)

### 6.14 参数只声明 `real`,SymPy 就判不了无穷远的收敛性

`∫_0^∞ e^{-tx}dx` 在 `t` 只有 `real=True` 时,SymPy 直接返回未求值的 Integral;
加上 `t>0` 立刻给出 `1/t`。
修法:先按**正数**重试一次再看有没有结果 —— 因为教材语境里 `a`、`b`、`s`、`t` 几乎
总是正的。而"参数到底要满足什么范围"不能因此含糊过去,要作为成立条件单独报出来。

### 6.15 参数的采样值,决定了正确结果会不会被误杀

参数采样原来按"没有正假设就取一正一负"来。于是 `∫_0^1 x^t dx` 在 `t=−1.5`
处发散,一个完全正确的闭式 `1/(t+1)` 被判定"未通过验证"。
修法:一律取正值采样(与教材语境一致),而"参数的有效范围"由
`_probe_conditions` 主动用敌意取值去探,作为条件报出来。

### 6.16 瑕点的阈值定高了,x^{-1/3} 这种"温和的无界"就漏了

端点是否有瑕点原来按"探针值 > 1e4"判断。`x^{-1/3}` 在 `1e-9` 处只有 1000,
于是漏判 → 没有做换元抹平 → 截断序列被端点奇点带偏 → 数值层报"无法判定",
而符号层明明已经给出了正确的 `π`。阈值改成 100。

### 6.17 中段"激进化简"之所以安全,是因为后面有验证门

三角替换后 `√(a²tan²t)` 会被写成 `a|tan t|`,带 `Abs` 的表达式常常积不动。
既然最终结果一定要拿原被积函数验证,中段就可以大胆地把 `|u|` 当 `u` ——
只在一个单调区间上求解,验证不过就整条作废。**先有验证,才敢激进。**

### 6.18 原函数的定义域可能不连通

`√(x²−a²)` 只在 `|x|>a` 上有实值,`x>a` 和 `x<−a` 是两个互不相干的区间。
数学上原函数只要求在**一个区间**上成立,所以验证器允许"某一个连通分支上的
采样点全部通过",并在报告里如实标注。这不会放过错误答案:
如果 `F'−f` 不恒等于 0,它在任何区间上都不会恒为 0。

### 6.19 节点直方图会给出"假相似"

`∫dx/(2x+5)` 和卡片例题 `1/(x²−1)` 的节点类型直方图余弦高达 **0.962** ——
两者的节点组成确实像,但方法毫无关系(一个凑微分、一个部分分式)。
原来"接近"的门槛放在 0.9,白白送出 1.5 分把部分分式推上了第一。

### 6.20 特征判定差一点点,推荐就完全错

- `x·e^{x²}` 外形上就是"多项式 × 指数",于是被推荐去分部积分 —— 但这是**错的**:
  正确方法是凑微分(`e^{x²}` 的导数正好带出那个 `x`)。
  判据补上:指数/三角的**自变量必须是一次式**。
- 单独一个 `cos x` 满足了"n 为奇数",被当成 `sinᵐcosⁿ` 奇次拆项题 ——
  其实它只是基本积分表里的一条。判据补上 `m+n ≥ 2`。
- 单独一个 `eˣ` 满足了"关于 eˣ 是有理函数"(把 `eˣ` 换成哑符号后就是它自己,
  分母为 1),被推荐去"令 t = eˣ"。判据补上:**分母必须真的用到那个哑符号**。
- `∫cos x/sin x dx` 被推荐去"积化和差"。判据补上:**化成和差必须要求两个不同的角**。

## 6b. 打通"换元 + 区间再现"的过程(第二轮踩坑)

第一轮做完之后,定积分评估里还剩三道题没做出来:
`∫_0^1 ln(1+x)/(1+x²)dx`(`(π/8)ln2`)、`∫_0^∞ x/(e^x−1)dx`(`π²/6`)、
`∫_0^∞ x^{s−1}/(1+x)dx`(`π/sin πs`)。修它们的过程又暴露出一批问题,
而且这批比第一轮更"架构性"。

### 6b.1 把递归求解塞进带超时的策略里,内层成果会被一起掐掉

第一道需要**两步组合**:先 `x = tan t` 化成 `∫_0^{π/4} ln(1+tan t)dt`,
再用区间再现公式。两步都在代码里,结果却始终是"未决"。

原因:换元策略在自己内部**递归调用** `solve_definite`。内层跑的是同一套策略、
花的是外层给的时间,于是外层那 30 秒超时把内层**刚刚算出来的结果**一起掐掉 ——
日志里写的是「换元换限 超时」,而内层其实已经把 `ln(1+tan t)` 积出来了。

修法是把结构改掉:换元只负责**产生**新问题(变换被积函数 + 反解新上下限,都是
廉价操作),求解交给一个**顶层调度的子问题队列**,新问题在自己的预算里跑;
算出结果后沿换元链映射回原变量,并对**原积分**做数值验证。

#### 这类问题的一般解法

"超时嵌套把内层成果掐掉"不是超时机制不好用,而是**用法错了**。
它其实分三个层次,前两个有通用解法,第三个只能靠架构:

**层次一 —— 预算不传播,内层的超时是假的。**
原来的代码里 `definite.py` 给一条策略 12 秒,而它内部调用的 `solve.py`
给每一次 `sp.integrate` 20 秒。外层 12 秒先开火,内层那 20 秒**永远用不到** ——
内层的超时形同虚设,连"以为还有 20 秒所以继续试下一种方法"的判据都错判了。
每个数字单看都合理,组合起来却没有意义。

解法:**用 `ContextVar` 把截止时间向下传播**,内层取
`min(自己想要的, 父层还剩多少)`。现在 `timeout.py` 里的 `remaining_budget()`
就是这个,实测三层嵌套(每层各请求 30 秒、最外层只给 2 秒)最内层拿到 2.00 秒。

**层次二 —— 外层到点放弃时,内层已经算出来的成果被一起丢掉。**
`run_with_timeout` 原来的做法是"到点就不再等,把结果盒子扔掉"。
解法:**成果在算出来的当下就交出来,别等最后 return**。
`ResultSink` 是一个线程安全的中转站,内层每验证通过一个原函数就立刻放进去;
外层即使超时放弃,调用方仍然能 `drain()` 出来。

本项目已经这么用了:定积分那边「牛顿-莱布尼茨」是整条流水线最贵的一步,
给它配了中转站;超时之后从里面把原函数抢救出来,**在超时之外**补算
`F(b)−F(a)`(那一步廉价且确定)。实测外层 2.45 秒放弃,
中转站里确实留下了内层验证通过的原函数。

**层次三 —— 抢救回来的可能只是"搜索到一半"的中间结果,未必可用。**
这一条是实测才看清楚的:那道题的第一次检查点交出的是一个带
`Piecewise`/`Abs` 的丑原函数(它验证通过了,但可读性差,所以 `solve` 还在继续
找更干净的那个),超时正好卡在中间。把它抢救出来之后,
`F(2a)−F(a)` 依然算不出来 —— **抢救只能拿回「已经算完的」,
不能把「还没算完的」变成能用的。**

这一层没有通用解法,只能靠**把超时的边界对齐到完整的工作单元**:
让被超时管辖的那一步本身是"要么完整做完、要么什么都没做"的粒度。
子问题队列做的正是这件事 —— 它把"又贵又不可控"的那一步
(找原函数)单独管起来,失败时不带走别的东西。

**一句话:超时的边界,必须和你"愿意丢掉的东西"的粒度对齐。**
只加超时、不做传播和成果外流,内层的成果注定被丢;
而想让超时之后的成果可用,还得保证被切的那一刀落在工作单元的边界上。

配了一个可复现的对照实验(`python _demo_timeout.py` 的思路已并入本节):
实验一验证预算传播穿过三层,实验二甲确定性演示成果跨边界,
实验二乙在真实代码路径上自动标定切点、演示前两层已解决而第三层仍然存在。


### 6b.2 队列顺序错了,子问题永远排不上

改成队列之后仍然不行:根问题的策略还没跑完,子问题就一直等;
等轮到它时预算已经耗光。

修法是把每个问题的策略分成**两拍**:

```
第一拍(便宜)  直接积分 / Beta / Bose-Fermi / 对称性
               → 生成换元子问题,插到队首
               → 自己以"第二拍"排在子问题之后
第二拍(昂贵)  牛顿-莱布尼茨 / 区间再现 / 费曼 / 级数
```

关键是"自己的第二拍要**紧跟在子问题之后**",而不是简单排到队尾 ——
队列顺序这种细节,差一步就是"答案近在眼前却永远轮不到"。

### 6b.3 化简要深入到对数里面去,而且候选要按简单度排序

`ln(1+tan t)` 的反射和是 `log(1+tan t) + log(1+cot(t+π/4))`:

- `sp.simplify` 完全不动它;
- `sp.logcombine` 能合并成 `log((1+tan t)(1+cot(t+π/4)))`,但外层 simplify
  还是动不了里面的**乘积**;
- 必须**先** `expand_trig` 把 `cot(t+π/4)` 展开,**再** logcombine,
  **再**把对数的**参数**单独拿出来化 —— 那个乘积恒等于 2,整个式子才塌成 `log 2`。

所以化简不是"一个 simplify 调用",而是一个**两阶段组合**。

还有一条同样重要:**候选要按 `count_ops` 排序再逐个试积分**。
不排序时这个策略单独跑一次要 **210 秒**,排序后 **0.19 秒** ——
因为 `sp.integrate` 对某些中间形式会挂很久,而真正能积的那个形式恰好最简单。

### 6b.4 数值层绝不能拿符号参数去做化简

第二道(`π/sin πs`)卡了半小时。定位到是**数值预检**:
它拿还带着符号 `s` 的被积函数去做"把无穷区间变换到有限区间",
而那一步里有 `sp.simplify((u/(1-u))**(s-1)/…)` —— 带符号指数的分式化简,
直接陷进去出不来。

数值层本来就不该处理符号参数:参数代值是调用方必须先做的事。
现在 `evaluate` 代完参数后会检查 `expr.free_symbols - {x}`,
非空就直接返回"无法判定";`_map_to_finite` 里也加了同样的闸。
**"数值层"这三个字意味着这里不应该出现任何符号运算。**

### 6b.5 参数的有效范围必须用来指导采样,否则会误杀正确答案

第二道的闭式其实早就被算出来了,却一直判"未通过验证"。
因为验证要采样参数,而采样取的是 `s = 0.5, 2.0, 5.0` ——
后两个不属于 `0<s<1`,在那儿**积分本来就发散**。

修法两条:
1. 把分支条件一路带到验证层,采样只在条件允许的范围内挑值
   (从候选池里筛出满足约束的,再错位搭配);
2. 牢牢记住:**参数的有效范围是答案的一部分**,不能含糊过去。

顺带一个细节:把参数临时换成正性符号重试时,条件里的 `s_pos` 也要换回 `s` ——
否则 `s not in (s_pos < 1).free_symbols` 成立,约束会被**静默忽略**。

### 6b.6 增值分析必须也套超时

第二道的主结果 0.8 秒就出来了,但整个 `analyze` 调用却卡住 ——
因为主结果之后还有两项**含参专项增值分析**(积分号下求导的数值检查、
尾部一致性探查),它们的内部有一处意外地慢。

结论很朴素:**增值功能必须有预算,绝不能把主结果拖住**。
现在这两项各自套 15 秒超时,超时就记一条"已跳过",不影响上面的答案。

### 6b.7 无穷限的首选方法要看振荡与否(修完又引入一次回归)

为了让代数衰减的尾巴(如 `x^{-1.5}`)收敛得好,我给无穷限加了
"线性分式变换映到 [0,1] + tanh-sinh"并放在最前面。
结果 `∫_0^∞ sin x/x dx` **回归成未决**:振荡积分做这个变换之后,
在 `u→1` 处振荡频率趋于无穷(`sin(u/(1-u))`),tanh-sinh 完全失效。

修法:振荡检测提到前面,**只有非振荡型才用这个变换**。

这已经是这一轮第三次"修一个东西、坏另一个东西"。教训是:
策略组合里**顺序本身就是语义**,不是可以随便插的;
每加一条策略都要把整张回归表重跑一遍。

### 6b.8 标准结果的缺口得靠卡片补,不能指望 CAS

第三道 `∫_0^∞ x/(e^x−1)dx = π²/6`(黑体辐射的 Stefan–Boltzmann 律要用它),
SymPy 是**完全放弃**的:直接积分、`meijerg=True` 都返回未求值的 `Integral`。

它的推导要把 `1/(e^x−1)` 展开成几何级数 `Σ e^{−nx}` 再逐项积分得到 `ζ(s)`,
而不是在 `x=0` 做泰勒展开(那样得到 `1/x − 1/2 + …`,积不出来)。
这属于"标准结果"而非"通用算法",所以补了一张卡片 `def_standard_bose_fermi`:

```
∫_0^∞ x^{s−1}/(e^{x} − 1) dx = Γ(s)·ζ(s)
∫_0^∞ x^{s−1}/(e^{x} + 1) dx = (1 − 2^{1−s})·Γ(s)·ζ(s)
```

**这正是"方法卡片"存在的意义**:CAS 的知识边界之外,还有一整片教科书标准结果。

## 6c. 性能优化(第三轮):「超时」只放弃了等待,没有放弃计算

第一轮的缺陷是**没有超时**;第二轮(6b.1)解决的是"超时会把内层成果一起掐掉"。
第三轮打开评估报告,发现最慢的 10 道题占了总耗时的 **87%**,而且其中 8 道是
含参积分 —— 于是问题变成:同样一套代码,为什么在评估里那么慢?

### 6c.1 超时不是免费的:跑飞的线程会毒化后面每一道题

先做了一次对照。同一道题,**单独跑**和**放在 50 题的串行评估里跑**:

| 题目 | 单独跑 | 评估报告里 |
|---|---|---|
| `∫_1^∞ x^{-1/2} dx`(发散) | 2.66 s | 11.16 s |
| `∫_0^∞ e^{-tx²} dx` | 26.34 s | 62.06 s |

慢 2.4 倍。评估是**纯串行**的,没有并行争抢,所以差的那部分只能来自一件事:
`run_with_timeout` 用守护线程实现,超时的语义是"到点不再等",**不是**
"到点停止计算" —— Python 杀不掉一个正在 C 层循环的线程。那个线程成为僵尸,
继续占着 CPU 和 GIL,把后面每一道题都拖慢。

三个发散题在报告里整齐地都是 10~11 秒,单独跑却只要 2.6 秒,就是同一个原因。

测出这件事之后,先试了本该最彻底的解:**常驻子进程 + `terminate()` 真杀 + 硬超时**。
结论是**当前环境不允许**:

```
ctx.Pipe()  →  PermissionError: [WinError 5] 拒绝访问
```

Windows 的 `multiprocessing` 用**命名管道**做 IPC,而沙箱拒绝创建命名管道。
所以这条路在这里走不通,只能退回进程内缓解(见 6c.2),并如实承认:
进程内缓解**不减少**已经跑飞的线程数,只是让数量有上界。

### 6c.2 同一个昂贵调用,被好几条策略各烧一遍预算

`∫_0^∞ e^{-t x²}dx` 的答案是**秒出**的,但"直接积分""牛顿-莱布尼茨"
"区间再现"都要各自算一遍同一个 `sp.integrate`,每次超时都各自烧满 12 秒。

新增 `cas.py` 作为唯一的闸口,做三件事:

* **记忆化**:同一个调用只发起一次,结果连"超时"一起留在进程里;
* **计量**:超时之后**留住线程句柄**,这样才能区分"还在跑"和
  "其实早跑完了,只是当时预算给少了" —— 后者放行重试,
  否则一次小额超时会把一个本来 3 秒就能算完的调用**永久封死**。

第三件事 —— "僵尸线程多了就限制新的长调用" —— **做过,又拆掉了**,
因为两版实现都造成了正确性回归。这段失败的尝试记在 6c.6,
它可能是这一节里最值得看的一条。

### 6c.3 增值分析不该默认做满

含参题的"积分号下求导"数值检查和"尾部一致性探查"是**增值**功能。
原来它们各给 15 秒、串行两段 —— 于是一道含参题允许在增值分析上烧掉 **30 秒**,
而这段开销对主结果毫无贡献。两步改动:

1. 两段**合起来共用一个预算**,由预算传播机制自动分配;
2. 默认**只在它可能带来新信息时才做**。主结果已经通过独立数值验证、
   而且它依赖的每个参数都已经报告成立条件时,再核对一遍不改变结论。
   结论弱(没解出来 / 参数范围仍未知)时才真正需要它。
   想强制做可以传 `supplementary=True`,跳过时报告里会写明原因。

### 6c.4 发散已经定了,就别再铺开全套符号策略

数值层是**策略 0**,先于任何符号尝试产生结论。它一旦判定发散,
符号搜索就从"找答案"降级为"复核"。

原来的代码不看这一点:发散结论已经拿到手了,策略循环照跑不误。
`∫_1^∞ x^{-1/2}dx` 里数值层一早就判出发散,却还要 11 秒才返回。
现在发散一确定就把窗口收窄(单策略 3 秒 / 合计 6 秒)——
复核仍然做,但不能和"还没有答案"时一样铺开。

### 6c.5 两极分化的策略,要给单独的短超时

"区间再现公式"的成败极其两极:能成的时候是**零点几秒**
(候选按 `count_ops` 排过序,试前 6 个就见分晓),不能成的时候就是一整段超时。
实测 `∫_0^{π/4} ln(1+tan t)dt` 上它烧满 12 秒,紧跟着的牛顿-莱布尼茨
也要 12 秒 —— 一道题先白等 24 秒。给它 4 秒:要么早就出来了,
要么基本可以断定出不来。

### 6c.6 熔断闸门:做了两版,两版都错,最后拆掉

僵尸线程会拖慢后面每一道题(6c.1),直觉的解法是"僵尸太多了就别再发起
新的长调用"。这个闸门我做了两版,**两版都造成了正确性回归**。

**第一版:直接拒绝。** 僵尸线程达到 2 个时,长调用一律不发起。
评估立刻从 45/45 掉到 **44/45**:掉的是 `∫_0^{2π}|sin x|dx`,
而它**单独跑 1.5 秒就出结果**。原因是它排在评估第 33 题,
前面已经攒下 2 个僵尸线程,于是这道**本可秒过**的题被整个跳过。

**第二版:改成降级**(僵尸 ≥2 时把长调用压到 2.5 秒,≥4 才拒绝)。
换了一道题掉:`∫_0^1 ln(1+x)/x dx` 需要超过 2.5 秒的直接积分,
被压缩之后超时。总分**还是 44/45**,而且总耗时反而涨了 71 秒
(被拒绝的调用现在会真的跑起来)。

根因是**判据本身错了**。闸门只能看到这次调用**请求**了多长预算,
看不到它实际要跑多久 —— 而"请求 12 秒、实际 1 毫秒"恰恰是绝大多数积分。
更要命的是它把**互不相关的题目耦合起来**:前一道题留下的僵尸线程,
决定了后一道题能拿多少预算。于是评估结果开始依赖**题目顺序**,
这已经不只是慢,而是不可复现。

所以闸门被拆掉了,只保留"计量"作为可观测指标。
真正减少僵尸的是**记忆化** —— 发起次数少了,泄漏自然就少。

**这几条经验比闸门本身值钱:**

* 熔断的判据如果用"请求量"而不是"实际消耗量",一定会误伤
  **请求很大、实际很小**的那类调用 —— 而它们恰恰最该放行。
* 任何跨请求的全局状态(闸门、缓存、配额)都会把请求**耦合**起来。
  耦合之后,单个请求的结果就不再只取决于它自己,可复现性随之消失。
  同一节里 `cas.py` 的**记忆化**也是全局状态,但它只缓存
  "同一个调用算出来什么"—— 那是一个**纯函数**,不随顺序变化;
  而闸门缓存的是"现在允不允许算",那**不是**纯函数。**这是两者的本质区别。**
* 于是有了一个可操作的判据:**全局状态只允许缓存纯函数的结果。**

### 6c.7 解释性元数据把答案拖住了 25 倍

优化完上面几条,不定积分总耗时反而从 78.6 秒涨到 100.1 秒。逐题看下去,
**一道题占了 82.8 秒**:`∫sin 3x·cos 5x dx`。

它本该是送分题(积化和差),而事实是:

```
裸 sp.integrate(f, x)      0.17s   ← 答案本身
solve()                  105.15s   ← 同样的答案
```

答案 0.17 秒就出来了。多出来的 105 秒花在 `step_trace()` 上 ——
它是用来在报告里展示"原函数是怎么一步步求出来的"那条**方法链**,
需要让 SymPy 的逐步积分器在整个规则空间里搜索。
profile 显示它引发了一场 `Basic.replace` / `_combine_inverse` 风暴
(56 万次 / 42 万次调用,还顺带算了 23 万次 `count_ops`)。

方法链是**解释性**元数据,不是答案的一部分。它不该有能力拖住答案。
现在它单独限时 4 秒,拿不到就给一条空链:

```
solve()  105.15s → 4.07s      (25 倍)
```

同一节里还顺手修了 `_rewrite_candidates`:它是"挑更好看的形式"用的
(答案已经验证通过之后才走这条路),原来是**先把 8 种变形全部算完再返回** ——
等于把 `sp.simplify` 这类可能几十秒的开销无条件付掉。现在改成**生成器**,
并且每个变形单独套 5 秒超时;调用方先查预算再取下一个,拿到干净结果就收工。

**教训:凡是"为了展示/为了更好看"的计算,都必须和答案本身分开计时。
它们的失败不能让答案失败,它们的慢也不该让答案慢。**

### 6c.8 评估器自己的假阴性

顺带发现"45/45 数值核对通过"这个数字本身是在一个**会误判的检查器**上测的。

`∫_0^∞ e^{-t x²}dx` 被计成 `value_match=False`,但系统给的
`sqrt(pi)/(2 sqrt(t))` 与标注的 `sqrt(pi/t)/2` 在 `t>0` 上**恒等**。
误判来自采样到了负数:两者在 `t=-0.5` 时一个是 `-1.2533i`、
另一个是 `+1.2533i` —— 主值分支的符号差异。

系统的约定是**参数默认取正**(也是 `parse.SYMBOLS` 的假设),
所以检查器现在只比正数采样点(仍然要求**所有**正采样点都一致,
不会放过真正写错的闭式)。

**教训:评估器也可能说谎,而且它的谎言方向和被测系统无关。**
修好之后 `value_match` 数字才可信。

## 6d. 扩充语料(第四轮)

性能问题解决之后(§6c),瓶颈只剩一个:定积分的检索。top-1 方法族命中 68%,
而且翻开朗报看,失败的方式很有信息量 —— 大半不是"缺知识",而是**评分和触发器
的结构性缺陷**。这一轮把语料从 24 张 / 72 例题扩到 26 张 / 122 例题。

### 6d.1 通用兜底卡永远拿 0 分

第一眼看到的怪事:`∫_0^1 x² dx` 的 top-1 是「对称区间上的奇偶性」。
可 `[0,1]` 根本不对称。

把分数拆开看就明白了(`Hit.explain()` 就是为此存在的):

```
def_symmetry_even_odd  总分 +6.44 = 触发条件 +1.75 例题相似 +1.84 例题命中 +3.00
def_newton_leibniz     总分 +5.58 = 触发条件 +0.00 例题相似 +2.68 例题命中 +3.00
```

两张卡的「例题命中」都是 +3.00,因为 `∫_0^1 x² dx` 和对称卡的例题
`∫_{-a}^{a} x² dx` **被积函数完全一样**,结构余弦都是 1.000。
差别全在触发条件:**牛顿-莱布尼茨是 +0.00**。

原因是它的四个触发字段**全是空数组**:

```json
"triggers": {"interval": ["any"], "has_radical": [], "has_func": [], "form": [], "misc": []}
```

而评分器的逻辑是"空字段和 `any` 一律跳过"(这个设计本身是对的 ——
否则声明一大堆条件的宽卡片会占便宜)。可当**所有**字段都空时,
这张卡就只能拿 0 分,连自己的例题都赢不回来。

修法不是给它加硬约束,而是给它**通配触发器**:声明它适用的全部区间与函数类型。
因为 coverage 会被摊薄(声明 8 个区间只命中 1 个),它大约拿到 +2.9 分,
足以赢过不该出现的对称卡,但仍然赢不过任何真正对症的卡片。

### 6d.2 例题命中分只认被积函数,不认区间

上面那 +3.00 暴露了第二个结构性问题:两张卡在**不同区间**上拿到同一个满分。

`∫_{-a}^{a} x² dx` 和 `∫_0^1 x² dx` 的被积函数相同、区间不同,
但"结构完全吻合"的判定只看节点直方图,与区间无关。
好处是宽容,坏处是**区间在最强的那条通道上不起作用**。

这一轮没有改这个机制(改它要重跑全部回归),但它是**已知的下一处优化点**:
把 `interval` 并入例题余弦,例如给区间单独一项权重。

### 6d.3 卡片在自己的例题上对不上

`def_improper_split` 原来声明 `interval: ["finite"]`。可它自己的三道例题是
`∫_0^1 x^{-1/2}dx`、`∫_{-1}^1 1/\sqrt{1-x²}dx`、`∫_0^1 \ln x dx` ——
区间标签分别是 `unit`、`symmetric`、`unit`。**一张卡在自己的例题上全部拿不到区间分。**

这类错误靠人眼看不出来,但 `build_corpus.py` 的"自命中"一跑就露馅。
这是"语料质量可以自动度量"的直接收益。

### 6d.4 卡片之间抢地盘:一个"越修越低"的指标

`def_convergence_p_test` 原来把 `unit`/`finite` 也写进了区间。
于是在 `∫_1^e 1/x dx` 这种**有界、收敛、能直接算**的题上,它抢到了 top-1。
p 判别法是**反常积分**的工具,区间已收回到无穷限。

更有意思的是"一般高斯积分"这张卡。它是我按教科书分类新开的,结果它把
`∫_0^∞ x³e^{-x}dx` 和 `∫_0^∞ x²e^{-x}dx` 都判成了高斯 —— 而那两题是
**Γ 函数形状**,该归 Beta/Gamma 卡。这是自测报出来的**跨族偏差 2 处**。

修的过程走了两步,两步都是错的,第三步才对:

1. 先把它的 `form` 从 `["composite","power"]` 收成 `["composite"]` —— **没用**。
2. 再把区间从 `["infinite","zero_to_inf","symmetric"]` 收成
   `["infinite","symmetric"]`,并删掉两条普通高斯例题 —— **还是没用**。
   收窄区间反而让 `∫_0^∞ e^{-tx²}dx` 的家族命中丢了 1 分(36/50),白亏。
3. 这时候才去看**根因**(见 6d.2):例题命中分只看节点直方图余弦,
   而 `x³e^{-x}` 和 `e^{-x²}` 这类**小表达式**的直方图会饱和到 1.000,
   于是"结构完全吻合"的 +3.0 分是**误报**的 —— 把例题删到只剩一条也照样误报。
4. 取消这张独立卡(Poisson 卡的 recipe 本来就写着"遇到 e^{−ax²+bx} 先配方"),
   并回去之后指标回到 **37/50、31/43**。

**但这里必须更正一个我先前的说法:取消这张卡并没有让跨族偏差消失,只是让它
换了张卡出现** —— 那 2 处偏差转到了 `def_standard_poisson` 名下。
偏差的**根因**是 6d.2(相似度会饱和 + 区间不参与),不是"多了一张卡"。
真正的修复在 6d.8。

**教训:当一个指标"越修越低"时,先怀疑自己的修法方向,而不是接受那个更低的数字。
这次低下去的那 1 分根本不是代价,是修错了地方。**

### 6d.5 硬规矩:写进语料的例题必须能真的解出来

`build_corpus.py` 对每一条例题跑完整流水线。这条规矩挡下了两个
"教科书上明明该有"的卡片:

* **Euler 对数正弦积分** `∫_0^{π/2} \ln(\sin x)dx = −(π/2)\ln 2`:
  三道候选**全部解不出来**。这是**能力**缺口,不是语料缺口 ——
  给它建一张卡只是让语料好看,而系统依然做不出这道题。
  如实记为待办,不为它建卡。
  **后来按"先补能力、再补卡"的顺序补上了(§6e)**,并在这里留下这条记录 ——
  包括当初为什么拒绝建卡。
* `∫_0^∞ \frac{\cos(ax)-\cos(bx)}{x}dx`:单独跑能出结果(约 30 秒),
  但放进自测就失败。边缘不稳定,予以剔除。

**如果不设这条规矩,这一轮本可以多报两张卡片、多 6 条例题。**
那些数字会很好看,但它们是假的。

### 6d.6 改语料会改变求解路径 —— 因此也会改变**耗时**

这是这一轮最意外的发现。语料变了 → 检索推荐变了 → `make_plan` 生成的代换变了
→ 求解走的路线变了。于是一个**原本 13 秒解完**的例题,
在语料改动之后**卡住不动**(实测单核跑了十几分钟没返回)。

查下来暴露出一个**真实的健壮性缺口**:`solve_definite` 里只有**策略**在
`guarded()` 的超时保护之内,而下面这几处全是裸调的:

| 裸调的地方 | 它在干什么 | 后果 |
|---|---|---|
| `evaluate`(策略 0) | 数值预检,定敛散 | 陷进去就没有墙 |
| `_verify_value` | 结果核对,每组参数各求一次积 | 同上,而且是答案的**必经关卡** |
| `_probe_conditions` | 探参数有效范围 | 同上(纯增值信息) |
| `_make_subproblem` | 换元换限,内部要 `sp.solve` | 同上 |

单条策略都有 12 秒上限,但这四处没有 —— 它们一旦慢下来就没人管。

### 6d.7 修这个缺口:第一次修是错的

**第一版给"结果核对"整体套了 15 秒上限。** 跑单条题看着挺好,但**累积负载下
`∫_0^∞ e^{-tx²}dx` 直接判成失败** —— 它单独跑 7.3 秒就能验证通过,
在跑过几道含参题之后需要超过 15 秒。**上限把"慢"变成了"错"**,比卡死更糟:
卡死至少是诚实的失败,而"慢→错"会安静地给出错误结论。

**第二版改对了**,关键是两点:

1. **闸门下沉到单次求积**(`_evaluate_bounded`,20 秒),而不是套在整个核对外面。
   失控的单位本来就是"一次求积",不是"一次核对"。上限也给得宽松 ——
   含参题合法地在几组参数上各求一次积,慢到十几秒是常事。
2. **把"求不出来"和"对不上"分开。** 原来的核对逻辑把两者都记进 `failures`,
   于是一组求积超时 = 一次否证 = 正确答案被丢掉。现在分三档:
   `confirmed`(支持)/ `contradicted`(**否证**)/ `unknown`(既不支持也不否证)。
   **通过的门槛一点没放松** —— 仍然是"至少两组独立确认、且零否证",
   只是不再把 `unknown` 当成 `contradicted`。

效果:

| | 修之前 | 第一次修(错) | 修好后 |
|---|---|---|---|
| `∫_0^∞ e^{-tx}\sin x/x\,dx` | 十几分钟不返回 | — | **6.0 秒** |
| `∫_0^∞ e^{-tx²}dx` | 20.5 秒 ✓ | 55.4 秒 ✗ | **17.4 秒** ✓ |
| `∫_0^∞ x^{s-1}/(1+x)dx` | 6.2 秒 ✓ | 39.4 秒 ✗ | **18.6 秒** ✓ |
| 完整语料自测 | **跑不完**(卡死) | — | **跑完** |

**教训:给"必经关卡"加超时时,超时必须下沉到真正失控的那一步,
并且要区分"没算出来"和"算出来不符" —— 否则超时本身就成了新的错误来源。**

### 6d.8 修掉 6d.2 的根因:给"例题命中"加一道结构门禁

6d.2 留下的话是"这一轮没有改这个机制(改它要重跑全部回归)"。这一轮改了,
因为它同时是**三个毛病**的共同根因。

问题在于"★例题结构完全吻合"这档加分只看**节点直方图余弦**。小表达式的直方图
会饱和:

```
cos(tokens(x³e^{-x}), tokens(e^{-x²}))  ≈ 1.000    → 误发 +3.0
```

`x³e^{-x}` 和 `e^{-x²}` 的直方图都是"几个节点",余弦几乎必然打到 1.000,
于是"完全吻合"被发给了一张方法完全不同的卡。同一件事的另一面是
**区间完全不参与**:`∫_{-a}^{a} x²dx` 与 `∫_0^1 x²dx` 也拿到同一个满分。

修法是**加门禁**:加分的余弦只在"结构签名一致"时才计入,
签名取 `has_func` / `form` / `interval` 三项。

```python
if self._same_shape(feats, ex_feats):     # has_func、form、interval 三集合相等
    best_cosine = max(best_cosine, cosine)
```

注意只改了 **加分的门禁**,没有动"相似度"本身(`example_term` 照旧),
所以影响面很小。效果:

| 指标 | 加门禁前 | 加门禁后 | 最初(未扩语料) |
|---|---|---|---|
| top-1 方法族命中 | 37/50 = 74.0% | **38/50 = 76.0%** | 34/50 = 68.0% |
| top-1 卡片命中 | 31/43 = 72.1% | 30/43 = 69.8% | 27/43 = 62.8% |
| **top-3 卡片命中** | 38/43 = 88.4% | **39/43 = 90.7%** | 39/43 = 90.7% |

top-3 回到了扩充语料之前的水平(扩语料时掉的那 1 道被这道门禁补了回来),
方法族命中再 +1;代价是 top-1 卡片命中 −1。**这是一次真实的取舍,不是纯赚**:
门禁让"最强的那条通道"变准了,但也让一些本来靠误报加分排到第一的卡片掉了下去。
按"方法族命中 + top-3"这两个更粗的粒度看是赚的,所以我保留了它。

**教训:一个会饱和的相似度(a≈1.000)不适合当"完全吻合"的判据。
要么换一个不会饱和的度量,要么再加一道离散的签名门禁 —— 后者改动小得多。**

## 6e. 补一个**能力**缺口:对数正弦积分

§6d.5 记着一件没做成的事:`∫_0^{π/2} \ln(\sin x)dx = −(π/2)\ln 2` 是教科书标准结果,
但三道候选例题**全部解不出来**。当时我把它记为"能力缺口,不是语料缺口",
并且**拒绝为它建卡** —— 这一步是对的:给系统做不出来的题建卡,
只是让语料看起来完整,系统依然不会做。

这一轮先把能力补上,再把卡补上。**顺序不能反。**

### 6e.1 为什么 CAS 不做:(这一族的)它全部放弃

`ln(sin x)` 没有初等原函数,`∫_0^{π/2}` 上的定积分也就不能靠牛顿-莱布尼茨。
实测 SymPy 的 `integrate` 与 `meijerg=True` 都返回未求值的 `Integral`,
级数展开路线也超时。

它的值只能靠**恒等式推导**得到,而且推的是一个**方程**而不是一个积分:

```
记 I = ∫_0^{π/2} ln(sin x)dx
1. 区间再现 x → π/2 − x,由 sin(π/2 − x) = cos x 得  I = ∫_0^{π/2} ln(cos x)dx
2. 两式相加                                        2I = ∫_0^{π/2} ln(sin x cos x)dx
3. 倍角 sin x cos x = sin(2x)/2,换元 u = 2x         = (1/2)∫_0^{π} ln(sin u)du − (π/2)ln2
4. 再用 sin u 关于 u = π/2 的对称性,∫_0^{π} = 2I     = I − (π/2)ln2
5. 代回第 2 步:2I = I − (π/2)ln2            ⇒      I = −(π/2)ln2
```

注意第 5 步:**I 出现在等式两边**。这不是"算出一个积分",而是"解出一个未知量",
所以它天然落在通用积分算法的能力之外。

### 6e.2 做法:和 Bose/Fermi 一样,由标准结果策略接手

新增 `_strategy_log_sine`(§6b.8 那条"标准结果靠卡片补"的路子):

* **识别**:用 `expand_log(..., force=True)` 把对数里的乘除拆开,把被积函数
  归成 `k0 + a·ln(sin x) + b·ln(cos x)`。于是 `ln(sin x cos x)`、
  `ln(tan x)`、`ln(sin²x)` 都自动落进同一族。
* **求值**:`[0, π/2]` 上是 `k0·(π/2) + (a+b)·I`;`[0, π]` 上要求 `b = 0`,
  值是 `k0·π + 2a·I`。
* **推导写进 docstring**,不是查表 —— 上面那五步一字不差地写在代码里。

`force=True` 会假设参数为正,**在这里是合法的**:本策略只在 `[0, π/2]` 与
`[0, π]` 上生效,而这两个区间**内部** `sin x > 0`、`cos x > 0` 恒成立,
端点只是零测集。这一点写在函数注释里,免得后人以为是随手放宽的。

效果:

| 题 | 修之前 | 修之后 |
|---|---|---|
| `∫_0^{π/2} \ln(\sin x)dx` | 18.0 秒,**失败** | **2.4 秒** ✓ |
| `∫_0^{π/2} \ln(\cos x)dx` | 失败 | **0.4 秒** ✓ |
| `∫_0^{π} \ln(\sin x)dx` | 失败 | **0.4 秒** ✓ |
| `∫_0^{π/2} \ln(\sin x\cos x)dx` | 失败 | **1.9 秒** ✓ |
| `∫_0^{π/2} \ln(\sin^{2}x)dx` | 失败 | **0.6 秒** ✓ |
| `∫_0^{π/2} \ln(\tan x)dx` | 失败 | **5.6 秒** ✓(由**区间再现**策略解出,不是本策略) |

最后一行是个有用的交叉验证:`ln(tan x) = ln(sin x) − ln(cos x)`,本策略会给出
`a=1, b=−1 ⇒ (a+b)·I = 0`;而**区间再现策略独立地也算出 0**。
两条互不相干的路线给出同一个值,再由数值层确认 —— 这正是这套系统的验证结构该有的样子。

### 6e.3 为什么敢写一个"推导公式"进代码

因为**验证门在后面**。如果我把那五步推错(比如漏掉 π/2),数值层会当场否掉它,
这个策略就只是白跑一趟,不会污染任何答案。**先有验证门,才敢写标准结果策略** ——
这是本项目里"验证不是装饰,是能力边界的一部分"的又一个例子。

### 6e.4 老实说清它的边界

* **只支持不带缩放的自变量**:`ln(sin(2x))` 不在内(那要再走一次换元)。
* **只在 `[0, π/2]` 与 `[0, π]` 上生效**。`[π, 2π]` 上 `sin x < 0`,
  必须写 `ln|\sin x|`,本策略不处理。
* 它是一条**为一族标准结果写的专门策略**,不是"解方程式的通用能力"。
  真正的通用做法是让系统自己识别出"I 出现在两边"并解这个线性方程 ——
  那属于 §9 里还没做的那类推理能力。
* 含 `ln(cos x)` 且区间为 `[0, π]` 的输入会被**显式拒绝**(cos 在那里变号),
  而不是硬算一个复数结果。

### 6e.5 卡片与评估题:先有能力,再补覆盖

能力补上之后才做这两件事:

1. 加入 `def_log_sine` 卡片(6 条例题,全部先跑过完整流水线确认可解);
2. **评估集也补题**(§9 第 12 项指出过:上一轮扩充了 50 条例题却一题没加评估题,
   所以新卡片的覆盖能力根本没被考到)。新增 6 道 **覆盖性测试**题
   (`d51`~`d56`),note 里逐条标明身份 —— 它们**不是随机抽样**,
   不该混进原有 50 题里冒充泛化能力,所以报告里按"原有 50 题 / 全 56 题"分开看。

## 6f. 结构性修复:让"超时"真的停止计算

这一节处理的是整个项目里最根深蒂固的一条:**超时只放弃等待,不停止计算。**
它不是一个 bug,而是**结构**问题 —— 前面第 6c 节的所有优化都在绕开它
(记忆化去重、限时复核、按需增值分析),自测的求解数在 116~128 之间浮动
也是它的残余。

### 6f.1 先更正我自己的一个错误结论

§6c.1 里我写过:进程隔离走不通,因为**沙箱拒绝创建命名管道**
(`ctx.Pipe()` → `WinError 5`)。这个观察是对的,但**结论错了** ——
被拒的只是**命名管道这一种传输方式**,不是 IPC 本身。这一轮实测:

| 传输方式 | 结果 |
|---|---|
| `multiprocessing.Pipe`(命名管道) | ✗ `PermissionError: [WinError 5]` |
| **localhost TCP socket** | ✓ 绑定、子进程连接、往返全部成功 |

所以"硬保证"的那条路**是通的**,只是要换传输方式。这个更正很重要:
它把"做不到"变成了"还没做"。

### 6f.2 实际采用的修法:异步异常注入

`PyThreadState_SetAsyncExc(thread_id, exc)` 可以往目标线程**异步注入**一个异常,
异常在目标线程的下一个**字节码边界**抛出。sympy 的 `integrate` 几乎全是
Python 层循环,所以这条注入真的能把它停下来。实测:

| | 进程 CPU 增量(1.2~1.5 秒窗口) |
|---|---|
| 对照组:跑飞的计算**放着不管** | 1.45 s(吃满一个核) |
| 实验组:**交给超时处理** | **0.00 s** |
| | **抑制 100%** |

注入信号刻意继承 `BaseException` 而不是 `Exception` —— sympy 内部到处都是
`except Exception`,继承 Exception 会被就地吞掉、线程照跑,注入就白做了。

### 6f.3 真正关键的结构性发现:杀掉的范围必须和放弃的范围一致

第一版只杀**直接子线程**,结果不生效。原因值得记下来,它是纯粹的结构问题:

超时是**分层**的 —— 外层策略一个 12 秒闸、内层 integrate 一个 20 秒闸。外层到点时:

```
外层线程 T1  ──阻塞在──▶  done.wait() 等待内层
                              ▲
                              │ 注入 T1 毫无作用:
                              │ CPython 只能在字节码边界抛异常,
                              │ 阻塞在锁等待里的线程到不了边界
内层线程 T2  ── 正在烧 CPU ──┘ 而 T1 **不知道 T2 的存在**,没人去杀 T2
```

**结果:外层报告"超时",里面那个计算继续跑满一个核。**

修法是给同一调用链上的线程建一个**家族**,超时时对家族里每个成员注入:

```python
_family: ContextVar[set | None]        # 子线程继承同一个集合
...
stopped = _stop_family(family, _KILL_GRACE)   # 整支一起杀
```

一句话:**杀掉的范围必须和你放弃的范围一致。** 这条和 §6b.1 那句
"超时的边界必须和你愿意丢掉的东西的粒度对齐"是同一件事的两面。

### 6f.4 判据也修过一次:不能数线程死活

第一版用"线程还在不在"当判据,结果不稳定(3/5 报"没杀掉")。原因是
**外层线程在内层被杀之后会恢复并继续干自己的活**(还在自己的预算里收尾)——
它是活着的,但并没有烧 CPU。用"死活"当判据是在测错东西。

真正要证明的是"不再有跑飞的计算占着核",所以改成**直接量进程 CPU 增量**
(上面的表)。这个判据也写进了 `tests/test_all.py` 的 H 组:
对照组必须确实在烧 CPU(证明测量本身有效),实验组必须接近零。

### 6f.5 老实说:这仍然不是硬保证

* 异常只能在**字节码边界**抛出。线程若卡在真正不返回的 C 代码里
  (例如装了 gmpy2 之后的大整数循环),注入会被推迟到它返回 Python 为止,
  等于杀不掉。此时退回"丢下不管",**不会更糟**。
* 打断是**任意位置**的。理论上可能在别人持有锁时把它带走 —— 但 CPython 的
  `with` / `try-finally` 在异常传播时照常释放锁,sympy 的全局缓存用的是
  `with _cache_lock`,而且缓存是"算完才写入",被中断只会少一条缓存,
  不会写进错的值。**这一点用测试固定住了**:H 组在杀完之后立刻再做
  `integrate` / `diff` / `simplify`,确认结果仍然正确 ——
  因为如果杀线程会污染缓存,那这个优化就是在拿正确性换速度,不能要。
* 因此它的定位是**尽力而为的清理**,不是资源隔离。

### 6f.6 剩下的结构性改进(还没做,但方向明确)

1. **嵌套超时本身就是错的形状。** 现在有 5 层左右嵌套的预算(策略 12 秒 /
   牛顿-莱布尼茨 12 秒 / integrate 20 秒 / evaluate 20 秒 / 子问题 10 秒),
   每一层都在"放弃等待",而真正失控的单位只有一个。
   干净的结构是:**只在最外层设一个边界**,里面全部改成**协作式取消**
   (现在已有 `budget_exhausted()` 这套机制)。层数少了,要杀的范围自然清楚。
2. **进程隔离才是硬保证,而它已经验证可行**(6f.1)。做法:
   父进程开 TCP 监听,用 `subprocess` 起 `python -m integral_rag.worker`,
   子进程连回来;失控时直接 `proc.kill()` —— 它是真的死,不是"尽力"。
   代价是每个问题一次进程启动(实测约 1~2 秒,可摊薄到"每个问题一个进程"
   而不是"每次 integrate 一个进程")。**要做常驻服务就应该走这条。**
3. **线程churn 值得治理。** 测试套件跑一轮创建了约 280 个线程,
   每个 `run_with_timeout` 一个。改成一个小线程池,或者干脆用 6f.6.2 的
   常驻子进程,都能把这块开销和复杂度一起降下来。

### 6f.7 效果:超时终于"省下"了 CPU

修好之后重跑评估,**正确性与检索指标一个都没变**,但耗时大幅下降:

| 指标 | 修之前 | 修之后 |
|---|---|---|
| 定积分 总耗时(56 题) | 176.4 秒 | **104.0 秒** |
| 定积分 平均耗时 | 3.15 秒/题 | **1.86 秒/题** |
| 不定积分 平均耗时 | 0.49 秒/题 | **0.43 秒/题** |

原因很直接:评估是**串行**的,而原来每次超时都会留下一个吃满整核的线程。
超时越多的题,后面被拖得越惨 —— 这也解释了为什么早先"最慢 10 题占总耗时 87%"
以及"同一道题在评估里比单独跑慢 2.4 倍"。现在超时真的把 CPU 还回来了。

把整条性能线连起来看,定积分平均耗时:

```
7.19 秒/题  →  3.04  →  3.11  →  1.86 秒/题
   最初        去重+限时  补硬超时  杀掉跑飞线程
                           (代价)    (结构性修复)
```

**总计 3.9 倍加速,而正确性与检索指标全程未动。** 中间那一步(3.04→3.11)
是唯一一次"变慢" —— 那是给`guarded()` 之外的裸调用补超时的代价,
而它正是最后这一步能成立的前提。

## 6g. 把解题步骤渲染出来(补上"没有分步解答"这条短板)

项目自评里反复出现过一条:**没有真正的分步解答**。报告里能看到的只有
一行 `采用策略:换元链:x = tan t(分母含 1+x²) → 区间再现公式`,
外加第 ⑦ 节一段**原始的**尝试记录。真正有价值的东西 —— **这条链本身** —— 恰好没被呈现。

### 6g.1 数据其实一直都在

`_Problem` 已经把一切都记下来了:

```python
@dataclass
class _Problem:
    f, x, lo, hi          # 这个子问题
    sub: Substitution     # 从父问题到自己用的那次换元
    parent: _Problem      # 父问题
    depth: int
```

`Substitution` 里还带着 `name`(人读的名字)、`x_expr`(代换式)、
`card_id`(依据哪张卡片)、`why`(为什么选它)。子问题队列把这些串成了一条链,
但从没被渲染过。新增的 `_describe_steps()` 就是走一遍 `parent` 指针,
把"原积分 → 每次换元 → 求解 → 等值性 → 验证"写出来。

### 6g.2 渲染时发现的一个**教学错误**

第一版渲染出来是这样:

```
第 3 步 · 求解:在内层问题上用「区间再现公式」得到 pi*log(2)/8
第 4 步 · 回代:沿换元链换回原变量 x,得到 pi*log(2)/8     ← 和第 3 步同一个数
```

"回代"这个说法是从不定积分那边照搬过来的。而**定积分的换元是等值变换** ——
上下限同时换掉,换元只是把这个积分改写成另一个**数值完全相同**的积分,
根本不存在"把结果换回原变量"这回事。照搬那套说法会让人以为还要再代一次。

现在渲染成:

```
第 4 步 · 等值性:换元只是把这个积分改写成另一个**等值**的积分
         (上下限同时变换),内层的值就是原积分的值,无需回代
```

只有当值**真的**含内层变量时才说"回代"(代码留着这条分支,实际上不该触发)。
这是"照搬另一个模块的措辞"会带来的典型错误 ——
**两条链的形状不一样,说法就不能一样。**

### 6g.3 效果

`∫_0^1 ln(1+x)/(1+x²)dx` 现在长这样:

```
① 结构特征 / ② 检索命中 / ③ 方法指导
④ 解题步骤
   第 1 步 · 原积分 ∫_{0}^{1} log(x + 1)/(x**2 + 1) dx
   第 2 步 · 换元:三角替换 x = tan t(分母含 1+x²) · 令 x = tan(t)
             · 依据卡片 def_substitution_limits · 把 1+x² 换成 sec²t,
               常与区间再现公式配合 ⟹ 化为 ∫_{0}^{pi/4} log(tan(t) + 1) dt
   第 3 步 · 求解:在内层问题上用「区间再现公式」得到 pi*log(2)/8
   第 4 步 · 等值性:…内层的值就是原积分的值,无需回代
   第 5 步 · 验证:对**原积分**做高精度数值求积核对 —— 通过(相对误差 0.00e+00)
   第 6 步 · 说明:区间再现公式:I = ½∫[f(x)+f(a+b−x)]dx(化简后为 log(2))
⑤ 结果与验证 / ⑥ 数值层 / ⑦ 尝试记录
```

发散题也有步骤,而且明确区分「发散」与「没算出来」:

```
第 2 步 · 敛散判定:数值层判定发散 —— 在 x=1 附近部分积分无界增长(一阶极点)
第 3 步 · 结论:该积分不收敛,没有有限值(这**不是**「没算出来」)
```

`as_dict()` 里也多了 `"steps"` 字段,结构化调用方拿得到同样的内容。

### 6g.4 顺手清掉两处死代码

* `attach_trace()` 定义了但**从来没被调用过** —— 它给 `DefiniteSolution` 填
  `trace` / `trace_var`,而报告里渲染 `trace` 的那段用的是**不定积分**的
  `Solution`(另一个类)。也就是说定积分这边这两个字段永远是空的。
  删掉,换成真正被渲染的 `steps`。
* 报告的小节编号原来是**写死**的 ①②③…,于是 `brief=True`(跳过若干小节)
  会跳号(渲染成 ①→②→⑤)。改成按实际渲染顺序生成,以后加小节也不会错位。

**教训:死代码不只是"占地方"。** 这两个字段看起来像"方法链已经有了",
实际上永远是空的 —— 不读渲染路径就很容易以为这条短板早补上了。

## 6h. 把不定积分那条链也接上(同一条短板的另一半)

§6g 接上的是**定积分**的换元链。不定积分那边还有一条断链,而且断得更隐蔽。

### 6h.1 报告里那段"方法链"其实在讲另一道题

原来的 `⑥ 方法链` 长这样:

```
⑥ 方法链(SymPy 逐步积分器给出的解题路径,变量 t)
   substitution
     u = tan(x/2)
```

它读起来像是"这道题怎么解的",但**变量是 t** —— 也就是说,当解法走了代换路线时,
这段路径描述的是**代换之后那个积分**。它看得出"用了什么规则",
但看不出**这段路径和用户问的积分是怎么接上的**:中间的原函数是在 `t` 里求的,
回代之后才变成 `x` 的表达式,而**回代这一步在报告里根本不存在**。

根因是 `Attempt` 少记了两个字段:走代换时只存了回代**之后**的 `result`,
没存回代**之前**的 `intermediate`(含 `t` 的原函数),也没存用的是哪次
`Substitution`。数据没记,报告自然接不起来。补上之后:

```
第 1 步 · 原积分 ∫1/(cos(x) + 2) dx
第 2 步 · 换元:万能代换 t = tan(x/2) · 令 x = 2*atan(t)(t = t)
         · 依据卡片 weierstrass_substitution · 三角有理式统一化为 t 的有理函数
         ⟹ 化为 ∫2/(t**2 + 3) dt
第 3 步 · 求原函数:对代换后的积分求原函数,得到 2*sqrt(3)*atan(sqrt(3)*t/3)/3(含变量 t)
第 4 步 · 回代:把 t 换回 x —— 得到 2*sqrt(3)*atan(sqrt(3)*tan(x/2)/3)/3
         (不定积分**必须**做这一步,否则答案还留在代换变量里)
第 5 步 · 验证:对结果求导回验 F′(x) ≡ 被积函数 —— 符号验证:差式经 simplify 化简为 0
```

规则库那段路径没有被删掉,而是**挂到第 3 步下面**,并标明它是"代换后那个积分"的展开。

### 6h.2 两条链的形状相反 —— 同一件事第二次撞上

§6g.2 记过一次:定积分换元是**等值变换**,说"回代"是错的。
不定积分**正相反** —— 不回代,答案就还留在 `t` 里。

同一个动作("把结果换回原变量")在两个模块里的地位**完全相反**:

| | 换元后要不要回代 |
|---|---|
| 定积分 | **不要** —— 上下限同时换了,内层的值就是原积分的值 |
| 不定积分 | **必须** —— 否则答案不是原变量的表达式 |

**所以步骤渲染不能写成一个共用函数。** 我把它写成了两个(分别在 `definite.py`
与 `solve.py`),并在两边都注明"和另一边的区别",防止以后有人图省事合并它们。

### 6h.3 顺带统计:实际走代换的只有 3.6%

把 56 道不定积分评估题实际走的路线数了一遍:

| 路线 | 题数 |
|---|---|
| 直接积分(SymPy 内置算法) | **53** |
| 代换 | 2 |
| 恒等变形 | 1 |

SymPy 的内置积分器太强,绝大多数题**第一次尝试**就解决了 ——
`plan.py` 辛苦规划出来的代换、以及那套方法卡片,实际很少被走到。

这**不影响正确性**(验证门照旧把关),但它解释了两件事:
① 这部分工作的价值主要体现在**可解释性**上(说清"这次到底是谁解的");
② 对方法卡片体系是个诚实提醒 —— **它目前的贡献主要在检索/教学层,不在求解层**。

### 6h.4 另外三处顺手修掉的

* **恒等变形没被说出来。** `恒等变形:因式分解` 不是换元(变量没变,只是把被积函数
  改写成更好积的形式),原来渲染成"用「恒等变形:因式分解」直接求",读者看不出答案
  是从哪个式子积出来的。现在单独一步说明改写成了什么。
* **验证只印一个 `symbolic`。** `_symbolic_verify()` 原来返回布尔值,报告就只能写
  "symbolic" —— 等于没说。改成返回**成功的那一级的名字**:现在写的是
  "求导后的差式经 `simplify` 化简为 0"或"差式直接为 0",证据链到底是哪一条一目了然。
* **拒答也有步骤了。** `∫x^x dx` 原来步骤是空的;现在写明"没找到能通过求导回验的
  原函数,系统选择不作答 —— 而不是编一个看起来像样的答案"。与定积分的发散结论对齐:
  **"没做出来"也该是一个有结论的结果,而不是一片空白。**

## 6i. 修一处"永远不会触发"的特征 token

§9 里挂着一行小字:`frullani_shape` 的判定逻辑是错的,对真正的 Frullani 积分
**永远不会触发**,因为当时没有任何卡片声明它,所以是死代码、优先级不高。

这一轮去修,结果发现它**错了两处、而且是互相独立的两处**——
少修任何一处,它照样不触发。

### 6i.1 第一处:判据写反了

```python
# 旧代码
terms = sp.Add.make_args(sp.expand(num))
if len(terms) == 2 and sp.simplify(terms[0] + terms[1]) == 0:
    feats.misc.add("frullani_shape")
```

注释写的是"两项互为相反数的东西之和"。可 Frullani 的分子是
**同一个函数在两个缩放下的差**:

```
f(a·x) − f(b·x)          ← 真正的 Frullani 分子
A + (−A) = 0            ← 旧判据要求的东西(即被积函数恒等于 0)
```

`simplify(terms[0] + terms[1]) == 0` 要求分子**恒为零**,
也就是说只有"被积函数 ≡ 0"才能通过。这个 token 自然一次都没亮过。
(顺带,那句 `simplify` 还是一处白留的卡顿点。)

新判据看的是结构:

* 分子恰好两项、符号一正一负;
* 两项的**数值系数绝对值相等**(`2e^{-x} − 3e^{-2x}` 不算);
* 两项是**同一个函数头**(`exp` / `sin` / `cos` / `atan` / `log` / 倒数…);
* 两个自变量都只是 x 的**常数倍**(`inner/x` 不含 x)—— 排掉 `f(ax+b)`;
* 两个缩放系数不相等(相等则分子恒为 0)。

### 6i.2 第二处:`together` 把分母改掉了(更隐蔽)

修完判据还是不通。查下去才发现取分子的方式本身就有问题:

```python
num, den = sp.fraction(sp.together(f))
if eq(den, x): ...
```

`sp.together` 会把 `exp(-a x)` 当成 `1/exp(a x)` 去**通分**:

```
(e^{-ax} − e^{-bx})/x   ──together──▶   (−e^{ax} + e^{bx}) / (x·e^{ax}·e^{bx})
```

分母再也不是 `x`,`eq(den, x)` 直接失败。也就是说:**指数型 Frullani 积分
在"取分子"这一步就已经出局了**,连判据都轮不到。

改成在**因子层**找那个 `1/x`,剩下的因子乘积当分子 —— 不做通分,不改变形状。

**这两处是独立的:修判据不解决通分,修通分也不解决判据。** 所以"这只是一个
写错的条件"这个判断本身就是错的 —— 它看上去像一处小 bug,实际是两层。

### 6i.3 修好之后

判别器在 11 个用例上全对(4 个真、7 个假):

| 输入 | 期望 | |
|---|---|---|
| `∫_0^∞ (e^{-ax}−e^{-bx})/x dx` | ✔ | 真 Frullani |
| `∫_0^∞ (cos ax−cos bx)/x dx` | ✔ | 真 Frullani |
| `∫_0^∞ (arctan 3x−arctan x)/x dx` | ✔ | 真 Frullani |
| `∫_0^∞ sin x/x dx` | ✘ | **Dirichlet 型,分子只有一项** |
| `∫_0^∞ (e^{-ax}+e^{-bx})/x dx` | ✘ | 相加不是相减 |
| `∫_0^∞ (2e^{-x}−3e^{-2x})/x dx` | ✘ | 系数不等 |
| `∫_0^∞ (e^{-(x+1)}−e^{-(x+2)})/x dx` | ✘ | 是 f(ax+b),不是缩放 |

`def_standard_frullani` 卡片也随之声明了 `misc: ["frullani_shape"]` ——
有了这个 token,它才第一次**有依据**把 Frullani 与 Dirichlet 区分开
(两者都是 `∫_0^∞ …/x dx`,原来只能靠例题相似度猜)。卡片里也补上了这条区分说明。

**一条经验:`simplify(...) == 0` 这种判据很容易写成"要求式子恒为零",
而它几乎总是错的。** 想判"两项是同一个东西的两种形态",
应该去比**结构**(函数头、系数、自变量关系),而不是去比"加起来等不等于 0"。

### 6i.4 顺带改了两条**测试期望**,过程留痕

修好之后评估里的 `d48`、`d49` 反而从"族命中"变成了"族未命中" ——
因为它们现在的 top-1 是 `def_standard_frullani`,而期望写的是 `parametric`。

查下去发现这两条期望**写于语料里还没有 Frullani 卡片的时候**:
那时唯一的通路是"积分号下求导/费曼技巧",所以只能标成 parametric
(`d49` 的 note 原文就是"费曼技巧必需")。§6d 新增了专属卡片之后,
这一族最该给的答案就是标准结果卡。**期望该更新,但必须留痕:**

| | 改前 | 改后 |
|---|---|---|
| `family` | `["parametric"]` | `["standard_result", "parametric"]` ← **两个都算命中** |
| `card` | `def_param_differentiation` | `def_standard_frullani` |
| `note` | — | 写明"为什么改、原来是什么" |

两条原则:①**只增不减**,旧期望仍然算命中;②**note 里写明**这是更新过的期望。
这样报告里既看得到新数字,也看得到它不是凭空挪动的门槛。

## 6j. 把时间花在哪弄清楚:一次按数据下手的调度优化

§6i 之后评估稳定在 **75.7 / 77.2 秒**(56 题)。继续优化的第一步不是改代码,
而是**先看时间分布** —— 结果非常集中:

| 题 | 秒 | 占比 |
|---|---|---|
| `d31 ∫_0^1 ln(1+x)/(1+x²)dx` | 32.4 | 27.6% |
| `d49 ∫_0^∞ (arctan ax − arctan bx)/x dx` | 22.5 | 19.2% |
| `d47 ∫_0^∞ e^{-tx²}dx` | 9.2 | 7.8% |
| 其余 53 道 | 平均 0.88 秒 | — |

**两道题占了 47%。** 所以这一轮只做两件事,都对着这两道题。

### 6j.1 补上 Frullani 策略:卡片有了,策略却没有

`d49` 的 22.5 秒来自**费曼技巧**绕路。而 §6d 我明明为这一族建了
`def_standard_frullani` **卡片** —— 检索会推荐它,但**求解侧没有对应策略**,
于是"检索说用 Frullani,求解却只能靠积分号下求导硬绕"。

这和 §6e 补对数正弦是同一件事,**只是顺序反了**:那次是先补能力再补卡,
这次是卡先来了、能力没跟上。补上 `_strategy_frullani` 之后:

| | 修前 | 修后 |
|---|---|---|
| `∫_0^∞ (arctan ax − arctan bx)/x dx` | 22.5 秒(费曼) | **2.5 秒**(Frullani) |
| `∫_0^∞ (e^{-ax}−e^{-bx})/x dx` | 4.7 秒 | **0.14 秒** |

判别直接复用 §6i 修好的 `_scaled_same_function` —— 它本来只为给检索打标签而写,
现在同时给求解用,**一处逻辑两处受益**。

### 6j.2 踩到的坑:`AccumBounds.is_finite` 是 **True**

`cos` 型的 Frullani 需要 f(∞) 的 **Cesàro 均值**(`cos` 在无穷远没有极限,
但它的均值是 0,代进公式才得到 `ln(b/a)`)。所以 `_frullani_limit` 先试普通极限、
失败再退回均值。结果 `cos` 那道题直接崩了:

```
TypeError: cannot determine truth value of Relational: b**2/a**2 < 1
```

原因是这个判断:

```python
direct = sp.limit(cos(u), u, oo)        # → AccumBounds(-1, 1)
if direct.is_finite:                     # ← True!
    return direct                        # ← 把"振荡没有极限"当成了"极限是 [-1,1]"
```

**`AccumBounds` 是一个有界集合,所以 `is_finite` 为真。**
于是振荡被当成了极限,带 `AccumBounds` 的表达式一路往下走,最后在 `simplify` 里炸掉。

修法是要求它**既是数、又不是 AccumBounds**:

```python
if direct.is_number and direct.is_finite and not isinstance(direct, sp.AccumBounds):
```

**教训:"这个值有限吗"和"这个值是一个数吗"是两个不同的问题。**
一个看起来完备的守卫(`is_finite`)漏掉了一整类返回值,而漏掉的后果不是"慢",
是**在几十行之后以另一种面目崩掉**。同类守卫都应该补一句 `is_number`。

### 6j.3 顺序也要改:识别器必须排在通用积分器前面

补完策略发现 `cos` 那道题**还是走了 28 秒的通用积分** —— 因为 `直接积分`
排在第一位,它慢悠悠地算出来了,识别器根本轮不到。

四个形状识别型标准结果(Beta / Bose-Fermi / 对数正弦 / Frullani)都只认一种形状,
**不匹配时几乎零成本放弃,匹配时是闭式**。把它们提到 `直接积分` 之前,
实测代价是 **56 道题合计 0.32 秒**(最慢一次 0.1 秒)—— 基本免费。
识别器的结果同样过数值验证门,认错了会被否掉并继续往下走,所以**没有正确性风险**。

### 6j.4 「直接积分」改成先探针、后重试

`直接积分` 在 56 道题上累计 35 秒,其中 **12 秒全是 `d31` 一道题的整段超时**;
**除它之外没有一道题的"直接积分"超过 1 秒**。

于是第一拍只给它 `DIRECT_PROBE_TIMEOUT = 4` 秒当**探针**,不行就先走结构化路线
(换元链 + 区间再现),最后在昂贵阶段末尾再用**足额预算**回来补一次。
`cas` 的记忆化不会挡住这次重试:上一次超时的线程已经被**杀掉**,
它记录的实际耗时(约 4 秒)小于这次预算(12 秒),`cas` 会放行 ——
这正好用上了 §6c 里"超时记忆必须能自我解除"那条设计。

`d31`:34 秒 → **26 秒**(冷启动)。

### 6j.5 一个**没有**做的改动,以及为什么

顺着 d31 的链路看,20 秒花在"先把子问题全部试完、才轮到根问题自己的区间再现"上
(而根问题的区间再现 0.2 秒就成功)。那能不能把区间再现也提前当探针用?

测了一下:**不行。** `_strategy_king_property` 在没有外层超时时,
在评估集上跑十分钟都跑不完 —— 它失败时要烧满上限。放进第一拍就等于让
**每道题**都白付最多 4 秒。所以它必须留在昂贵阶段。

**这条否定结论也是有用的:它说明"哪些策略可以提前当探针"不能凭感觉,
要看它失败时的代价分布。** 直接积分失败时是 4 秒(且只有一道题会失败),
区间再现失败时是 4 秒 × 每道题。

### 6j.6 效果

| | 修前 | 修后 |
|---|---|---|
| 定积分总耗时(56 题,同机干净复跑) | 75.7 / 77.2 秒 | **65.2 / 68.1 秒** |
| 定积分平均 | 1.35 / 1.38 秒 | **1.16 / 1.22 秒** |
| `d49` | 22.5 秒 | **2.5 秒** |
| `d31` | 32~34 秒 | **26 秒** |
| 正确性(求解/一致/发散/误报) | 51/51、51/51、5/5、0 | **全部不变** |
| 检索三项 | 45/56、37/49、46/49 | **全部不变** |
| 语料自测 | 125/128、0 条失败 | **不变** |
| 不定积分 | 56/56、98.2% | **不变** |

**约 13% 提速,而所有正确性与检索指标一个都没动。**

> ⚠ 这一轮也让我看清了**耗时波动有多大**:同一份代码,`d31` 在同一个进程里
> 第一次跑 34 秒、第二次跑 6.7 秒(`d54` 是 7.5 → 1.0 秒)。
> 原因是 `cas` 记忆化与 SymPy 自身的缓存被前面的题预热了。
> 所以单次总耗时的横向对比**不可靠** —— 上面那两个数字是同机、清空
> `__pycache__` 之后的干净复跑,而且我删掉了 `__pycache__` 才发现
> "第一次跑特别慢"其实是**重新编译字节码**。这类环境噪声必须写出来,
> 否则很容易把噪声当成优化效果。

## 7. 已知边界与失败案例

**能做好的**:一元初等不定积分;正常/反常/无穷限/带参数的定积分;
教科书级的经典定积分(Dirichlet、Fresnel、Poisson、Wallis、Beta/Gamma、区间再现)。

**能力边界(如实记录)**:

- `∫x^x dx`:**拒答**。没有初等原函数,SymPy 也找不到特殊函数表达。
- `∫e^{x²}dx`、`∫sin(x)/x dx`、`∫e^{eˣ}dx`、`∫sin(x²)dx`:会给出
  `erfi` / `Si` / `Ei` / Fresnel S 等**特殊函数**形式的原函数。不是初等解,
  但确实通过了验证。报告里不会假装它是初等函数。
- ~~`∫_0^1 ln(1+x)/(1+x²) dx`(值 `(π/8)ln2`):**目前未决**。~~
  **已解决**(第 6b 节):换元 `x = tan t` + 区间再现公式两步组合能算出来,
  只是这条链最慢(约 36 秒,是全评估集里最慢的一题)。
- `∫_0^∞ x/(e^x−1)dx`(`π²/6`)、`∫_0^∞ x^{s−1}/(1+x)dx`(`π/sin πs`)等
  含参/反常题**均已解决**(见第 6b 节)。定积分评估集里 45 道收敛题
  **全部做出并通过验证**(45/45)。
- `∫dx/(x²+1)²` 推荐的是"不可约二次因子部分分式"卡片,而更省事的是递推公式。
  **两者都成立**,只是优先级没排对。
- 中文文本通道(按描述查方法)排序还不够准:查"根号里面是平方差",
  top-1 是欧拉替换(2.50),更贴切的三角替换排第 2(2.36)。
  这是 BM25 汉字二元组匹配的固有局限,调权重修不好。
- 定积分的**一致收敛只能否证、不能证明**。数值方法给不出数学证明。
- 超时之后那个守护线程还在后台跑(Python 无法中断 C 层循环),
  会占一个核直到进程退出。
- 参数符号默认取正(`a`、`b`、`n`、`s` 等教材惯例)。需要负参数的题请显式代入数字。
- 只支持一元积分。重积分、曲线/曲面积分、留数法不在范围内。
