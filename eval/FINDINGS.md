# 评估协议与实测结论

> 目标不是"多测几个指标",而是把**点估计**升级成**带不确定性与显著性判定的结论**。

## 一句话说清为什么需要它

原来的报告长这样:`求解率 56/56 (100%)`、`族命中 55/56 (98.2%)`、`与标注闭式一致 51/51 (100%)`。

这些数字**没有一个带区间**。而 56/56 的 Wald 区间宽度是 **0** —— 也就是说它会告诉你
"成功率 = 100% ± 0",把一个"我没测出问题"说成了"没有问题"。改成 Wilson 区间是
`[93.6%, 100%]`,这才是诚实的说法,也是面试里能被追问得住的说法。

## 怎么跑

```bash
# 测试(受限环境下需要关掉两个插件,正常终端直接 pytest tests/ 即可)
pytest tests/ -q -p no:cacheprovider -p no:tmpdir

# 生成报告(自带 summary/逐题一致性自检)
python eval/run_eval.py            --k 4 --json eval/report.json
python eval/run_eval.py --definite --k 4 --json eval/report_definite.json

# 把某个指标顶成主指标,以便比较不同策略
python eval/metric_view.py eval/report_definite.json \
    --field card_hit_top1 --gate expect_card -o eval/runs/def_top1.json
python eval/metric_view.py eval/report_definite.json \
    --field card_hit_top3 --gate expect_card -o eval/runs/def_top3.json

# 配对比较
python eval/compare.py eval/runs/def_top1.json eval/runs/def_top3.json \
    --metrics ok --label-a "top-1" --label-b "top-3"
```

## 结论一:不定积分的检索排序**已经到顶**,不值得做 reranker

| | 命中率 | 95% Wilson |
|---|---|---|
| 只看 top-1 | 44/45 = **97.8%** | [88.4%, 99.6%] |
| 放宽到 top-3 | 45/45 = **100.0%** | [92.1%, 100.0%] |

Δ = +2.2%,**分歧对只有 1 道** → McNemar 精确 p = **1.0000**。

按观测到的分歧率,要 80% 功效检出这个差异约需 **351 道配对题**(现在只有 45 道)。

**处置:不要在不定积分上投 reranker。** 这 1 道题不值得任何工程投入。

## 结论二:定积分有 **18.4%** 的净空间,值得投入

| | 命中率 | 95% Wilson |
|---|---|---|
| 只看 top-1 | 37/49 = **75.5%** | [61.9%, 85.4%] |
| 放宽到 top-3 | 46/49 = **93.9%** | [83.5%, 97.9%] |

Δ = **+18.4%**,95% 配对 Bootstrap CI = **[+8.2%, +28.6%]**,分歧对 9 道(净改善 +9),
McNemar 精确 p = **0.0039**,Holm 校正后仍是 0.0039 → **显著改善**。

**处置:定积分的 top-1 排序是真的短板。** 一个 reranker 最多能拿回 9 道题(18.4%),
而且这个提升在统计上站得住 —— 这是本仓库目前**唯一一处被证明值得投入的检索优化**。

## 结论三:检索深度 k 是**惰性的**

k=4 与 k=8 跑出来**逐题完全相同**(不定积分 56/56、55/56、44/45;定积分 51/51、45/56、37/49)。

说明这套系统实际只用到了 top-1,`k` 不是一个有效旋钮。**调 k 不会改变任何结论**——
这一点原来看不出来,因为只看点估计时"没变化"和"没测出来"长得一样。

## 一个反直觉但重要的推论

McNemar 精确检验**以分歧对的数量为条件**,所以:

> **单纯扩大评估集不会提高判别力。**

从 56 题扩到 200 题,如果新增的题两版表现都一样,检出能力**一点都不会提高**,
纯粹白花标注预算。要提高判别力,只能**针对性地补那些"两版确实会分歧"的题**。

`compare.py` 会直接把这个门槛算出来打印:
「49 道题时,净改善至少要 6 道(12.2%)才可能被判为显著。」

## 协议覆盖到哪一层

| 层 | 现状 |
|---|---|
| L1 检索层 | ✅ Hit@1、Hit@3(卡片/方法族)、配对显著性 |
| L2 生成层 | ⛔ 不适用(本系统无 LLM 生成) |
| L3 端到端 | ✅ 求解率 / 值一致率 / 发散判定正确率 / 耗时 |
| L4 统计严谨性 | ✅ Bootstrap CI、Wilson、McNemar、Holm/BH、检出能力门槛 |
| L4 待补 | ⛔ MRR / NDCG;⛔ 分层抽样标注;⛔ 人类标注一致性(Kappa 已实现但本仓库暂无人工标注数据) |

`evallib/stats.py` 里的 Kappa / Fleiss' Kappa / ECE 目前**在本仓库还用不上** ——
它们是为 `llm-eval-toolkit` 的后续场景(LLM-as-Judge 一致性、置信度校准)准备的,
已经过 scipy 交叉验证并有测试。**不要因为"没用上"就把它们删掉**,但也不要
在 integral-rag 的报告里假装用过。

## 过程中查出的 bug(留痕)

评估代码最危险的地方在于:**它错了也不会崩,只会安静地给出一个很像样的数字。**
下面四个都是这一轮真实撞出来的。

1. **`run_eval.py` 在管道里跑会中断。** Windows 控制台是 GBK,而脚本打印 ✅/❌,
   重定向时抛 `UnicodeEncodeError` —— "能不能跑评估"变成了"你在哪个终端里跑"。
   已统一把 stdout 切成 UTF-8。

2. **`value_match` 逐题字段恒为 `False`(且已提交进仓库)**。
   `record.update({...})` 的字典字面量里写了 `record.get("ok", False)`,
   读的是**这次 update 之前**的字典,永远拿到默认值。
   症状:summary 说 `value_match: 51`,逐题数出来 **0/56** —— 两个数字直接矛盾,
   而下游任何按题分析读的都是逐题字段。现在生成报告时会**自检**,
   summary 与逐题对不上就拒绝出报告(`_audit_summary`)。

3. **`cochrans_q` 把矩阵形状解包反了**(条件数当成题目数)。由与 scipy 的
   交叉验证测试抓出 —— 手写公式时这类错误肉眼很难看出来。

4. **`compare.py` 里把 `McNemarResult.n_pairs` 写成了 `.n`**。
   这个 bug **只在结论是"证据不足"时才会崩**,而"证据不足"恰恰是最常见的结果。
   之前跑真实数据时全是"逐题相同",所以一直没暴露。由测试抓出。
